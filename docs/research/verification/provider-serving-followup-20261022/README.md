# Provider serving follow-up — October 22, 2026

Customer: an operator requesting a GPU policy server needs requested/configured/registered provider facts and a failed strict startup if an explicitly primary TensorRT provider is unavailable.

Implemented locally, not committed or released: explicit TensorRT entries receive FP16/workspace/cache defaults while preserving order and caller options. Real Jetson detection bounds default builder workspace to a quarter of physical shared RAM, at most 4 GiB; an explicit argument or TETHER_TRT_WORKSPACE_BYTES overrides it. Workspace is not a total or peak memory cap and does not establish model fit. /config execution_providers reports requested, configured and registered providers/options, with precision and node placement explicitly not measured. SmolVLA, Pi0, inherited Pi05 and the legacy server enforce the explicit primary provider. Runtime RTC horizons are labeled planned runtime schedules, not physical consumption.

Before implementation, the four focused regressions produced 3 failures and 1 pass (before.log.gz). The final focused provider, original provider, strict mode and RTC adapter suites passed 59 tests (final.log.gz). Ruff passed on changed files (ruff-final.log.gz). Tests use mocked ORT sessions and an isolated home; no GPU, actual engine build, numerical parity, physical consumption or on-board memory acceptance was exercised. The source hashes bind these receipts to this lane; neighboring CLI/proof/loader changes have separate owners.

Read-only Studio integration review identified the startup/stop and delayed-preflight races, which the parent owns. It also found alternate public dispatch bypasses: direct native PyTorch ignored ORT provider arguments, and split Pi0.5 passed bare provider strings without defaults or strict per-stage checks. The four new regressions failed before the fixes (dispatch-before.log.gz). Explicit ORT intent now selects ONNX ahead of an ambient TETHER_NATIVE override for primary and shadow, while direct native construction rejects ORT provider arguments. The split wrapper builds separate plans/cache paths for VLM prefix and expert, validates both actual sessions before readiness, and preserves per-stage configured/registered options in /config. The summary is explicitly a union of stage registrations; precision and node placement remain not measured. Mixed stage primary providers report a mixed mode rather than a requested-device label. The underlying primitive forwards distinct provider lists to each session; combining this new stage override with its existing CUDA graph override fails actionably instead of discarding intent. Existing capture-only callers are unchanged.

The final alternate-dispatch/split/CreateApp suite passed 34 tests (dispatch-final.log.gz), with mocked provider sessions and a local lifespan, with no model inference, downloads or GPU. The existing split test fixture was extended with explicit session registration facts because readiness now validates them. Ruff passes for the split source and focused tests. The untouched native file has a pre-existing unused torch.nn import (original line185), separately observed; it was not removed as part of these fixes. No new target/model qualification is claimed.
